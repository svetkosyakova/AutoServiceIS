# Правила работы над проектом

## 1. Общие положения

Проект: информационная система «Автосервис».

Дисциплина: «Проектирование информационных систем».

Тема курсового проекта: тема 13 — ИС «Автосервис».

Репозиторий используется для хранения исходного кода, документации и материалов курсовой работы.

## 2. Правила работы с Git

* Основная ветка проекта — `master`.
* Все новые задачи выполняются в отдельных ветках.
* Новые ветки создаются от актуальной версии `master`.
* Название ветки должно соответствовать формату `feature/<номер-issue>`.
* Перед началом работы над задачей необходимо создать GitHub Issue.
* После завершения задачи изменения отправляются в GitHub и оформляются через Pull Request в `master`.
* Прямые коммиты в `master` после первоначальной настройки проекта не выполняются.
* При создании Pull Request преподаватель `MarinaPaley` указывается в качестве проверяющего.

## 3. Правила оформления коммитов

Сообщения коммитов должны быть краткими и отражать суть изменений.

Рекомендуемый формат: `<тип>: <краткое описание>`.

Используемые типы:

* `feat` — добавление функциональности;
* `fix` — исправление ошибки;
* `docs` — изменение документации;
* `test` — добавление или изменение тестов;
* `build` — изменение конфигурации сборки;
* `refactor` — изменение кода без изменения его функциональности.

Примеры:

* `docs: add project conventions`
* `feat: add service catalog`
* `fix: correct order cost calculation`
* `test: add work order tests`

## 4. Правила оформления кода C#

* Используется язык программирования C#.
* Для именования классов, методов и свойств применяется PascalCase.
* Для локальных переменных и параметров методов применяется camelCase.
* Названия должны отражать назначение элементов программы.
* Один класс рекомендуется размещать в отдельном файле.
* Для форматирования кода используются стандартные соглашения C#.
* Неиспользуемые переменные и ненужный код следует удалять.
* Для доступа к членам текущего экземпляра класса допускается использование `this`, когда это улучшает читаемость или необходимо для устранения неоднозначности.

## 5. Комментарии и документация

* Комментарии должны пояснять сложную логику, а не повторять код.
* Для публичных классов и методов рекомендуется использовать XML-комментарии C#.
* XML-документация оформляется с помощью тегов `summary`, `param`, `returns` и `exception`, когда они применимы.
* Документация проекта хранится в файлах Markdown с расширением `.md`.
* Материалы, предназначенные для включения в курсовую работу, оформляются в Microsoft Word (`.docx`).

## 6. Организация проекта

Информационная система «Автосервис» предназначена для управления заказ-нарядами, клиентской базой, автомобилями, услугами и загрузкой механиков.

Основные сущности системы:

* Клиент;
* Автомобиль;
* Проблема или неисправность;
* Услуга;
* Мастер;
* Заказ-наряд.

Основные функциональные возможности:

* ведение прейскуранта услуг;
* формирование заказ-нарядов;
* расчёт стоимости работ;
* учёт выработки механиков за период;
* применение скидок для постоянных клиентов.

## 7. Проверка изменений

* Перед отправкой изменений необходимо проверить состояние Git.
* В репозиторий не следует добавлять временные файлы, секреты, пароли и локальные настройки.
* Перед объединением Pull Request необходимо убедиться, что автоматические проверки GitHub Actions завершились успешно, если они настроены.
* Изменения должны соответствовать требованиям текущей задачи и не нарушать существующую функциональность.

## 8. Работа с GitHub Issues

* Каждая отдельная задача должна иметь собственный Issue.
* Issue должен содержать понятное название и описание ожидаемого результата.
* Ветка создаётся с использованием номера соответствующего Issue.
* После выполнения задачи Pull Request должен ссылаться на соответствующий Issue.
* Issue закрывается после выполнения задачи и принятия изменений, если иное не предусмотрено заданием.
